# Karaoke Search — QA and usability pass

The subsequent `20260907-4` personal-library/picker release is documented in [FEATURE_RELEASE.md](FEATURE_RELEASE.md). This report preserves the earlier review and performance evidence.

Initial usability pass completed 2026-09-07 at version `20260907-2`; the follow-up below verifies version `20260907-3`. This includes the six earlier review fixes and a broader pass over finding, filtering, saving, organizing, and sharing songs. Changes remain local and have not been deployed. Production headers were inspected read-only during the follow-up.

## Result

The tested journeys pass. Thirteen regression scenarios, the full-catalog smoke suite, and nine axe checks pass in each of Chromium, Firefox, and WebKit. Chromium's actual accessibility tree also confirms modal names, accessible Undo, and background exclusion. Controlled upgrade/offline checks pass in all three engines. These checks do not certify accessibility or replace physical-device testing.

### Startup measurement

Three fresh Chromium contexts per version, a local static server, 4× CPU slowdown, no service worker, no concurrent test workload for the final measurement. The baseline is the saved pre-change app from this working session. Values are medians; they are not field measurements or phone benchmarks.

| Metric | Before | After |
| --- | ---: | ---: |
| Longest startup task | 1,923 ms | 147 ms |
| Total startup blocking time (sum beyond 50 ms per long task) | 1,938 ms | 174 ms |
| Time until catalog/results ready | 2,500 ms | 2,601 ms |

The longest pause fell about **92%**, with a roughly 0.1-second increase in total startup time in this comparison. Shorter tasks let the browser service input between batches. The large JSON parse and first render can still produce tasks over 50 ms; startup is not completely free of blocking work.

All 36,734 prepared song records, normalized filter Sets, promoted tags, available options, popularity threshold, and ranked IDs were serialized and hashed before/after. Both produced SHA-256 `97a50b2d3d812f4853641122428b7c05d79b38c79eaa126de9ec7c4fc630cdbd`. No catalog data was edited.

The implementation schedules preparation batches at background priority when the Scheduler API is present, with a timer fallback otherwise. This permits other queued work to run between batches; see the [Chrome scheduling explanation](https://developer.chrome.com/blog/use-scheduler-yield). Retry and backup import are guarded against overlap, and asynchronous preparation is awaited before reporting success.

## Verification performed

- Thirteen regression scenarios in Chromium, Firefox, and WebKit: native share payload/cancellation/failure, singer edit/blur/reorder, added state, exact artist/reload/group/focus, narrow mobile filters, catalog retry/invalid backup, clear Undo safety, draft Undo invalidation, empty search/Favorites actions, live facet counts, old/new QR import, mobile focus and nested dialogs, and icon availability/dimensions.
- Existing smoke suite: Discover, search, highlighting, add, decade filter, Browse, and no uncaught page errors.
- Nine axe checks per engine (27 total): search at 1440, 1024, 768, 390, and 320px; mobile filters; mobile setlist/Undo; dark search/Undo; QR dialog. Zero reported violations in these checks.
- Real-catalog checks: automatic fuzzy fallback (`dancign queen`), accent-folded search (`beyonce`), OR within decades and AND with genre, actual headless-browser clipboard copy, simulated clipboard denial, reorder and singer persistence, pagination from 160 to 320 entries, landscape reflow, and offline reload of all 36,734 songs.
- Earlier review fixes rechecked, including all raster app icons loading offline, legacy QR entries resolving, empty result scopes staying empty, and modal focus containment.
- Syntax, asset-version consistency, and whitespace checks pass. CI now runs smoke, regression, accessibility, and offline suites across three engines. Browser dependencies remain development/test tools; the site still has no runtime package dependencies or build step.

## Remaining device and deployment checks

Actual iOS Safari, Android phones, VoiceOver/TalkBack, phone keyboards/safe areas, OS installation prompts, and real native share sheets still require device testing. Viewport emulation and browser accessibility trees do not reproduce these completely.

A physical-device handoff should cover:

1. Type a song while loading, open/scroll filters with the keyboard visible, rotate the phone, and confirm all actions remain reachable.
2. With VoiceOver/TalkBack, search, add a song, edit its singer, remove/Undo, and open/close the QR and import dialogs. Check spoken labels, focus order, and background exclusion.
3. Install from the browser, launch from the home screen, enable airplane mode, and reload/search the songbook with a saved setlist.
4. Open native Share, complete a share, then repeat and cancel. Confirm the text includes singers and that cancellation does not disturb the setlist.

The local upgrade test simulates two versions of the current implementation. It does not replace validation of a real deployment transition from the currently live release. Production still serves `20260715-9`; none of this session's changes have been deployed.

Production HTML/manifest headers revalidate as expected, but the live `/sw.js` response returned `Cache-Control: public, max-age=14400, must-revalidate`, despite this repository's zero-age worker configuration. Versioned worker registration provides a new URL per release. After deployment, verify the served app version and the worker headers through the CDN, then test a real existing installed client upgrading. CDN configuration was not changed during this pass.
